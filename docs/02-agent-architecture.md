# 02 — Agent Architecture (LangGraph)

## 1. The agent model: hybrid ML + LLM

Every agent follows the same **hybrid** pattern over a **shared transaction
representation**: a fast, deterministic ML signal drives the numeric verdict; an LLM
produces the human-readable rationale and evidence. This satisfies the explainability
principle without putting an LLM on the critical latency path for the *score* itself.

The shared representation is built once per transaction by `representation-service`
(unified features + graph signals) and read by every agent, so all decisions see the
same signals — delivering unified, consistent intelligence across every agent.

```text
         SHARED TRANSACTION REPRESENTATION  (built once, read by all agents)
         (unified features + graph signals + hot features)
                               │
                   ┌───────────┴───────────┐
                   ▼                        ▼
         ml-scoring-service          agent-specific slice
         (XGBoost/LightGBM)          (reads its features from the shared repr)
                   │                        │
                   └───────────┬────────────┘
                               ▼
                      score + top features
                               │
                               ▼
                      llm-gateway (rationale)
                   "explain this score as evidence"
                               │
                               ▼
          Verdict { decision_hint, score, confidence, rationale, evidence[] }
```

- The **score** gates the decision and is produced in ML time (sub-50ms).
- The **rationale** is generated by the LLM from the score + top contributing
  features. If the LLM is slow or unavailable, the agent still emits a verdict with a
  templated rationale (graceful degradation — the decision never blocks on the LLM).

## 2. Two LangGraph graphs

LangGraph is used at two levels:

### 2.1 Orchestrator graph (`commerce-orchestrator`)

A stateful graph that drives the whole transaction evaluation.

Nodes:

1. `build_representation` — call `representation-service` to build the shared
   transaction representation (unified features + graph signals from Neo4j + Redis).
2. `fan_out` — publish `txn.evaluate.requested` with the representation attached;
   register expected verdict set.
3. `collect_verdicts` — await `agent.verdict.produced` events (with deadline).
   Conditional edge: `all_received` → `decide`; `deadline` → `decide_partial`.
4. `decide` / `decide_partial` — call `decision-engine`.
5. `execute` — on APPROVE/ROUTE call `payment-processor-sim`; else short-circuit.
6. `finalize` — emit terminal event, persist decision trace.

The representation is built in the orchestrator (not per agent) so it is computed once
and shared, avoiding six duplicate feature builds and guaranteeing every agent scores
against identical inputs.

State is checkpointed (LangGraph checkpointer backed by Redis/Postgres) so a crashed
orchestrator resumes mid-evaluation — this is what makes the agentic flow durable and
production-shaped rather than a single in-memory request handler.

### 2.2 Per-agent graph (each of the six agents)

A small, uniform graph reused by every agent (behavior differs by injected policy and
model):

1. `parse_request` — read `txn.evaluate.requested`, take the agent's slice of the
   **shared representation** (no separate feature build — the orchestrator already did
   it).
2. `gather_signals` — only agent-specific lookups not already in the representation.
3. `score` — call `ml-scoring-service` with the agent's model id.
4. `reason` — call `llm-gateway` for rationale + evidence (with fallback template).
5. `assemble_verdict` — build the `Verdict`, publish `agent.verdict.produced`.

## 3. The six agents

| Agent | Primary signal | Graph/feature inputs | Output verdict |
|-------|----------------|----------------------|----------------|
| **Risk** | Credit/behavioral risk ML model | customer history, velocity, prior defaults, amount vs. baseline | `risk_score 0–1`, decision_hint APPROVE/CHALLENGE/DECLINE |
| **Fraud** | Fraud ML model + graph anomaly | device graph, shared-entity rings, IP/geo, velocity bursts | `fraud_score 0–1`, decision_hint |
| **Routing** | Per-route health scorer | success rate / cost / latency per candidate route, merchant preference | **scores every route**, returns ranked routes + `chosen_route` |
| **Policy** | Rules + compliance | KYC status, sanctions flags, per-merchant limits, geo rules | `allow/deny`, violated_rules[] |
| **Merchant** | Merchant config | merchant SLAs, risk appetite, allowed methods, overrides | `preference adjustments`, soft constraints |
| **Checkout Personalization** | Method-success predictor | per-customer method history, success-by-method, instrument availability | ranked payment methods, `recommended_method` + confidence |

Each agent's model id and policy are config-driven, so adding a seventh agent is a new
service from a template, not a change to the orchestrator.

### 3.1 Routing as route-scoring (precision routing)

The routing agent does not merely pick a processor. It enumerates the candidate routes
available for the transaction's method/currency/merchant and scores each on predicted
success × cost × latency, returning a ranked list and the `chosen_route`. Scoring every
route in real time and selecting the healthiest before the payment is attempted
maximizes success rate, and the ranked list gives the decision engine fallbacks for
processor failure (see `06-api-contracts.md` §5).

### 3.2 Checkout personalization

Predicts which payment method is most likely to succeed for this customer (based on the
customer's method history and success-by-method signals in the shared representation)
and returns a ranked recommendation. In the demo this surfaces as a "recommended
method" in the decision response; in production it would feed a checkout UI. It is an
**advisory** agent — it never vetoes a decision.

## 4. Verdict schema (agent → orchestrator)

```json
{
  "event_type": "agent.verdict.produced",
  "event_id": "uuid",
  "transaction_id": "txn_...",
  "trace_id": "uuid",
  "agent": "fraud",
  "produced_at": "2026-10-08T12:00:00Z",
  "verdict": {
    "decision_hint": "DECLINE",
    "score": 0.87,
    "confidence": 0.91,
    "rationale": "High fraud likelihood: device shared across 4 recent chargebacks...",
    "evidence": [
      { "signal": "shared_device_ring_size", "value": 4, "weight": 0.42 },
      { "signal": "velocity_1h", "value": 11, "weight": 0.31 }
    ],
    "model_version": "fraud-xgb-2026.10.01",
    "degraded": false
  }
}
```

`degraded: true` indicates the LLM rationale fell back to a template (score still
valid). The decision engine treats degraded verdicts as full-weight on score,
reduced-weight on narrative.

## 5. Decision engine aggregation

The decision engine turns six verdicts into one decision using a **configurable
strategy** (default: weighted veto).

Default strategy:

1. **Hard vetoes first.** If `policy` returns deny, or `fraud_score ≥ fraud_block`,
   the decision is DECLINE regardless of others (safety-first).
2. **Weighted score** for the remaining APPROVE/CHALLENGE band:
   `composite = w_risk·risk + w_fraud·fraud` with configurable weights.
   - `composite ≤ approve_max` → APPROVE
   - `approve_max < composite ≤ challenge_max` → CHALLENGE (step-up auth)
   - else → DECLINE
3. **Routing** overlays the top-ranked route on an APPROVE and carries the ranked
   alternatives for failover.
4. **Merchant** applies soft constraints (e.g., force CHALLENGE for high-value even if
   APPROVE).
5. **Checkout personalization** is advisory only — its `recommended_method` is attached
   to the decision for the checkout surface but never changes APPROVE/DECLINE/CHALLENGE.

Missing-verdict policy (deadline hit):
- Missing `risk` or `fraud` → fail-safe to CHALLENGE or DECLINE (configurable).
- Missing advisory agents (`routing`, `merchant`, `checkout-personalization`) →
  proceed with defaults (routing falls back to the merchant's default processor).

Output:

```json
{
  "transaction_id": "txn_...",
  "decision": "CHALLENGE",
  "composite_score": 0.63,
  "strategy": "weighted_veto",
  "route": "processor_b",
  "route_alternatives": ["processor_a", "processor_c"],
  "recommended_method": "upi",
  "contributing_verdicts": ["risk", "fraud", "routing", "policy", "merchant", "checkout_personalization"],
  "explanation": "Approved band exceeded due to risk 0.58 + fraud 0.41; step-up required.",
  "degraded_agents": []
}
```

Every decision — inputs, strategy, weights, and output — is persisted as a
`decision.rendered` event so it is fully reconstructable (explainability principle).

## 6. Durability & failure behavior

- Orchestrator state is checkpointed per transaction; restart resumes.
- Agent consumers commit offsets only after publishing their verdict (at-least-once);
  idempotent verdict keys dedupe.
- A dead agent delays only its own verdict; the deadline + missing-verdict policy keep
  the transaction progressing.
